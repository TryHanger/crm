## 0. Цель и условия

Реализовать **полноценный рабочий frontend Business CRM** на базе дизайна из `готовый фронт.html`. Сопоставить его с разделом CRM в `платформа саас.html` при наличии в проекте; `готовый фронт.html` считать основным референсом. В CRM должны реально работать экраны и бизнес-операции, а не только показываться компоненты из макета. Сохранить уже работающий Booking Web, Booking Engine, ORM, RLS и E2E. Не проектировать заново бренд и не заменять дизайн шаблонной админ-панелью.

**Продукт:** один frontend CRM на `app.<root-domain>` для всех компаний; после авторизации доступны только свои членства `crm_memberships`. Данные и доступы в каждом запросе scoped по tenant и, где требуется, branch. Пользователи CRM: `owner`, `admin`, `master` с проверкой действий на backend. Клиенту публичной записи CRM аккаунт не требуется. Отдельная внутренняя `Platform Console` — не часть этого этапа.

**Первое обязательное действие:** снять инвентаризацию оригинального HTML по каждому состоянию и сравнить её с текущим React. Оформить `docs/CRM_DESIGN_API_MATRIX.md`: раздел → экран/состояние → маршрут → API → модель/таблица → минимально разрешённая роль → desktop/mobile reference → статус DONE/PARTIAL/NOT_IMPLEMENTED → E2E. Не ставить DONE, если API только возвращает заглушку или кнопка без операции.

## 1. Маршруты и структура frontend

Создать отдельные маршруты с общим `CrmLayout` и ролевой навигацией. Например:

```
/login
/accept-invite
/overview
/calendar?date=YYYY-MM-DD&branch=UUID&view=day|week|list
/customers
/customers/:id
/staff
/staff/:id
/services
/online-booking?tab=rules|appearance|publish
/reports
/settings/branches
/settings/users
/settings/company
```

Это пример маршрутов, не требование ломать публичные URL без необходимости. Допускаются nested routes. Основной принцип: навигация, прямое открытие и обновление URL действительно восстанавливают контекст выбранного экрана. Использовать отдельные modules/features/components; не разрастать `apps/business-crm/src/App.tsx` до нескольких тысяч строк. API-клиент централизован, авторизация и tenant context единообразны, повторных ручных fetch с расхождением контрактов нет.

Обязательные UI-state: loading/skeleton, empty, error/retry, validation, permissions/forbidden, disabled/readonly для истекшей подписки, сохранение (pending/success/failure), запрос перед опасными действиями. Отдельно мобильный layout с адекватной навигацией и карточками вместо неуместных больших таблиц.

## 2. CRM — календарь, запись и рабочее время (приоритет A)

Референсы: «День: сетка мастеров», «Запись выбрана», «Новая запись», «Новая запись: время не подходит», «Перенос: перетаскивание на другого мастера», «Отменённые показаны пунктиром, время свободно», «Блокировка времени», «Отмена записи: подтверждение», «Неделя: один мастер», «Неделя: вся команда», «Список записей», мобильные экраны.

**Функциональность:** день/неделя/список; дата, сегодня, фильтр мастеров, филиал; колонки мастеров; смены, перерывы, blocks, time off и фактические бронирования; адекватная визуализация пересекающихся и длинных визитов; карточка клиента с реальными услугами, ценой, статусом, историей и разрешёнными действиями. Наличие и цвет записи не должны быть единственным источником статуса — нужен текст. Любой state после reload восстанавливается из БД.

**Ручное создание:** филиал → клиент (поиск по телефону; создание с обнаружением дубля) → услуги → мастер с персональной ценой → свободное время → commit. Использовать тот же Booking Engine, что и клиентская запись. Создание, перенос, отмена и блокировки должны повторно проходить backend-валидацию, а не лишь визуальное изменение карточки. Для drag-and-drop обязательно показывать предварительные новые мастер/время/стоимость и выполнять серверный reschedule; при 409 вернуться к исходному положению. Для MVP drag-and-drop можно реализовать после формы переноса, но в матрице это обозначить PARTIAL, а не DONE.

**Статусы:** confirmed → arrived → in_progress → completed; cancelled/no_show при разрешённых переходах. Не показывать неразрешённые операции мастеру/администратору. Сохранять `booking_events` и `version` для контроля конфликтов. Отменённые записи при необходимости видимы для истории, но не блокируют доступность.

## 3. Клиенты (приоритет B)

Дизайн: список, поиск/фильтры, карточка, мобильные варианты, «найден дубль по телефону», «ничего не найдено».

Реализовать настоящие: paginated/sorted список, поиск по имени и E.164 телефону, создание и редактирование профиля, выявление дубля в рамках tenant, история бронирований, заметки и теги если предусмотрены дизайном. Каждая заметка имеет автора/время; запрет чужого доступа. При одинаковом номере у разных компаний создаются независимые customer records. Никакого default `marketing_consent=true`. Мастер видит только клиентов, к которым имеет разрешённый доступ по своим записям; не выдавать ему общую базу.

Если в backend отсутствует `GET /customers/{id}`, полноценный PATCH, pagination или history — добавить реальные маршруты, Pydantic response и integration tests. Проверить не только HTTP 200, но и соответствие значениям из PostgreSQL.

## 4. Сотрудники, услуги, индивидуальные цены, графики (приоритет B)

Дизайн: команда, профиль, назначенные услуги и индивидуальные цены, недельные смены/редактирование смены, мобильные версии.

Реализовать: создание/деактивацию сотрудника, связывание с пользователем/ролью/филиалами, `online_bookable`, график на неделю, перерывы, исключения, отпуск/time off; назначение услуг мастеру, персональных `price_override` и `duration_override` по филиалам при необходимости. Правила конфликтов между филиалами, лимиты тарифов, права владельца/админа. Редактирование смен не должно молча уничтожать уже записанные визиты; дать блокирующую ошибку или безопасное решение с подтверждением и аудитом.

Добавить недостающие реальные `GET/PATCH/PUT/DELETE` API с валидацией и миграциями только там, где требуется. Изменение предложения/графика должно влиять на **новые** слоты публичного Booking Web, но не переписывать цену и длительность уже созданных `booking_items`.

## 5. Каталог услуг и цены (приоритет B)

Дизайн: категории, список, трёхколоночный редактор, предупреждение «услуга без мастеров», мобильный режим.

CRUD категорий и услуг, порядок сортировки, базовая цена в minor units и длительность, филиальная доступность, активность/архивирование, связанные мастера. Валидация цены, длительности, названия; запрет несогласованных связей с чужим tenant. Архивирование без разрушения истории визитов. Чистый save/reload с проверкой отражения изменений в публичном каталоге.

## 6. Настройки онлайн-записи и публикация (приоритет C)

Дизайн: вкладки «Правила», «Внешний вид и предпросмотр», «Публикация: ссылка и QR», мобильные варианты.

Рабочие политики: book-ahead, min advance, cancellation cutoff, self-reschedule, slot interval, max services. Брендинг: название/логотип/акцентные цвета, предпросмотр действительно использует текущие значения. Управление публикацией и ссылкой конкретной компании; QR генерация на основе verified URL, никаких несуществующих URL. В публичном Booking Web правила и тема приходят из API. Оплата/SMS не должны выглядеть подключёнными без интеграции.

## 7. Обзор, отчёты и настройки компании (приоритет C)

Дизайн: обзор, отчёты, филиалы и рабочие часы, пользователи/роли, мобильные настройки, справочники и роли мастера.

Обзор: записи за выбранный период, статусы, ожидаемая выручка, загрузка; корректно различать **плановую стоимость услуг** и **реально полученные платежи**. Не выдавать сумму bookings за полученную выручку. Фильтр периода/филиала/мастера, timezone-aware агрегирование. Никаких выдуманных KPI.

Филиалы: создавать, редактировать адрес, телефон, timezone, статус, расписание, лимиты тарифа. Пользователи: список membership, приглашение, активация, роли, отзыв доступа; для существующего аккаунта приглашение не сбрасывает пароль. Отдельные права owner/admin/master, никаких self-elevation, tenant owner должен управлять только своей компанией. Мастер: только личное расписание, разрешённые данные своих клиентов и профиль. Поддержка readonly/запретов в зависимости от подписки и фактических backend entitlements.

## 8. Backend/API обязательства

Сначала сравнить реальные endpoints `apps/api/app/api/v1/business/routes.py` с дизайн-макетом, потом добавлять недостающие. В текущей базе есть `/calendar`, `/bookings`, `/customers`, `/staff`, `/services`, `/booking-settings`, `/reports/overview`; **наличие базовых GET/POST не означает готовности полноценных редакторов**. В `CRM_DESIGN_API_MATRIX.md` отметить отсутствующие PATCH, detail/history, графики и приглашения.

Контракты генерировать/проверять по `apps/api/openapi.json`; обнаруженные расхождения устранять на границе типизированного `packages/api-client`, а не подменять `data.staff || data.masters` навсегда. Убрать `any` там, где определимы DTO. Use `tenant_id` из проверенных `crm_memberships`, `X-Tenant-ID` только с server-side membership verification. Для tenant-owned таблиц RLS и FK scope. Тесты чужого tenant и чужого staff обязательны для каждого CRUD класса. All writes atomic, audited when necessary, server-side validation. Закладывать idempotency для создания записи.

## 9. Отложенный P1 backlog, не блокирующий старт CRM

1. **Time-first preview — не настоящая availability.** Сейчас без услуг `apps/booking-web/src/App.tsx` отображает синтетические часы `10:00–19:00`, создаёт `pref_*` слоты, преобразует время через фиксированный `-5` и после реального поиска может выбрать **первый другой слот**, если исходного времени нет. Оформить как «желаемое время (не подтверждено)», использовать timezone филиала без фиксированного смещения; если точное время недоступно, **не переключать молча**, предложить альтернативы с явным подтверждением. Добавить E2E «выбранное предпочтение недоступно».
2. `DateTimeStep.tsx` и `SummaryCard.tsx` местами жёстко используют `Asia/Almaty` или дату браузера. Пропускать `branch.timezone_iana`, проверять полуночные переходы и другой TZ.
3. В текущем `BookingEngine.create_booking` public создаётся при валидном `quote_id` **или** `expected_price_minor`; это не идентично требованию «только quote». Зафиксировать и тестировать политику, избегать ложного слова «strict quote required».
4. В `docs/KNOWN_LIMITATIONS.md` многие компоненты названы PRODUCTION-READY; до независимых security/performance/backup/deploy gates заменить на `DEV-VERIFIED`/`PILOT-CANDIDATE`. Workflow CI **не содержит `docker build`**: успешный Vite build/pytest/E2E не является проверкой production Docker image.
5. Legacy seed Modern Cut содержит `BH-*` референсы, хотя новые записи генерируют `MC-*`; объяснить это историческими fixtures или обновить тестовые seed без переписывания реальных исторических кодов.
6. Quote storage growth, rate limiting public API, реальная доставка приглашений, secure token storage/rotation, backup/restore & load tests — отдельный Production Gate, не симулировать.

Эти пункты можно исправлять в рамках первых CRM этапов без остановки разработки, но нельзя оставлять обещание production-ready.

## 10. Этапы исполнения (каждый — со своим коммитом, CI, демонстрацией)

**CRM-0 (архитектура UI + API contracts):** матрица по исходному HTML, общий layout, маршрутизация/навигация, права, типизированный API-client, реальные loading/error/empty states, CI в рабочем состоянии.

**CRM-1 (календарь):** довести day/week/list, real create/transfer/cancel/block/status, карточку записи, мобильный вариант. Запись созданная в клиентском сайте появляется в CRM. Разные tenant и master scoping.

**CRM-2 (клиенты + сотрудники + графики + услуги):** закончить связанный CRUD с backend-валидацией, индивидуальными ценами и сквозным влиянием на Booking Web. После смены услуги/смены новые свободные слоты изменяются правильно.

**CRM-3 (настройки + онлайн-запись + отчёты + пользователи):** реальное сохранение, preview/publication/QR, отчёты из фактов, филиалы и роли, владелец/админ/мастер. Сравнение desktop/mobile с дизайн-референсами.

**CRM-4 (gate):** полный аудит изоляции, роли, таблица состояния всех кнопок/форм, Playwright VRT, N+1/performance checks, accessibility basics, чистая БД с миграциями, DEV compose, README. Исправить backlog P1 или честно обозначить partial; не маскировать нереализованное.

## 11. Приёмка: обязательные интеграционные/браузерные проверки

Без условных `if (element.isVisible())` для обязательных проверок; тест должен падать, если важная запись или компонент отсутствует. Запуски на чистой test DB, не подменять бизнес-тестами мок-данные frontend.

- Owner A логинится → видит только компании своего membership; admin/master получают свои права; unauthenticated → login.
- Booking Web создаёт бронь → Calendar(day) показывает конкретный `booking_id`, `public_ref`, мастер/услугу/цену → week и list показывают тот же факт → reload сохраняет.
- CRM создаёт бронь вручную → Booking Web больше не показывает занятое время; race concurrent create сохраняет максимум одну.
- CRM переносит/отменяет → Booking Web availability освобождает/занимает корректные интервалы; история событий сохраняется.
- Мастер не может просмотреть/создать/изменить чужую запись или общий список клиентов при отсутствии права.
- Календарный block/time off/смена и перерыв меняют availability в публичном Booking Web; конфликт со существующим визитом обрабатывается.
- Owner редактирует базовую цену услуги и master-specific override → сайт показывает правильное «от» и authoritative quote; историческая booking сумма не меняется.
- Клиент создан из CRM, найден дубль по E.164 в том же tenant; такой же телефон другого tenant независим.
- Изменение book-ahead/cancellation-policy реально отражается на создании/отмене публичного визита и тексте UI.
- Публикация online-booking off блокирует публичные новые записи на backend, не удаляя исторические записи.
- Филиалы/смены/роли ограничены тарифом и доступом; отказ серверный, не только disabled-кнопка.
- Overview/report отражает реальные количества/статусы и не выдаёт плановую стоимость за оплаченный revenue.
- Прямой URL, refresh, back/forward, mobile width 320/360/390/768, desktop 1280/1440; нет критичного overflow.
- Desktop/mobile screenshot comparison с соответствующими состояниями в `готовый фронт.html`, количественные расхождения и объяснения в отчёте.
- Separate PostgreSQL test database guard, Alembic migrations, `pytest`, frontend builds, Playwright, no secrets in Git.
