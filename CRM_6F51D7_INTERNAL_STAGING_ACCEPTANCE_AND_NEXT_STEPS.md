## II. Границы доказательств и обнаруженные замечания

### A. Тестовый стенд не является готовым публичным развёртыванием

`verify_staging_deployment.py` записывает `.env.staging` с **фиксированными строками** паролей PostgreSQL, runtime-пользователя, JWT и начального platform owner. В коде они названы случайными/криптостойкими, но значения постоянны; это допустимо только как изолированный, одноразовый CI-fixture при гарантированном `--teardown`, но недопустимо при запуске доступного кому-либо STAGING или production. Нужно генерировать секреты через `secrets` или получать их из защищённого хранилища. Не переиспользовать этот env вне CI. Убедиться, что `--teardown` выполняется и при исключениях (finally/GitHub cleanup).

### B. TLS-проба не проверяет привязку сертификата к hostname/SNI

Функция `test_https_request` создаёт `HTTPSConnection("127.0.0.1")` и принудительно ставит `ctx.check_hostname=False`; отдельный `Host` header не доказывает корректность TLS SNI/hostname validation. Шесть проб подтверждают HTTPS-ответы и маршрутизацию по HTTP Host, но не доказывают корректный доверенный сертификат для домена. Для независимого подтверждения использовать DNS-resolve к loopback (например, curl `--resolve` + `--cacert`) либо кастомное соединение с `server_hostname=<requested_hostname>`, `check_hostname=True`, с отрицательным тестом неверного hostname. Self-signed CA с `BasicConstraints(ca=True)` подходит только для изолированного теста, не для боевого доступа.

### C. Пользовательский E2E пока не проходит через контейнерный Nginx

В CI сначала выполняется Docker smoke, затем стек останавливается, а Playwright тесты идут в `ENVIRONMENT=development`, с demo seed и портами 8000/3000/3001/3002. Подтверждены два отдельных факта: (i) контейнеры и базовый HTTPS-прокси работают, (ii) пользовательский SaaS flow работает в DEV. Единый сквозной процесс в контейнерном STAGING с реальными hostnames, SNI, без demo seed **не проверен**. Перед первым внешним реальным пилотом нужен как минимум один такой тест: owner invite → CRM → публикация → переход по полученному QR URL → реальное бронирование → карточка в CRM; pause → 404.

### D. Дополнительное укрепление

- `Dockerfile.frontend` запускает финальный процесс от root (директива `USER nginx` отсутствует после обновления, использован `chown` в CMD). Для пилота разнести сборку/инициализацию томов и непривилегированный runtime; проверить read-only и Linux capabilities.
- Реальные бэкапы вне хоста, расписание и восстановление из offsite ещё **BLOCKED**. Значение RTO из SQL restore нельзя считать измеренным RTO всей платформы; выработать эксплуатационный runbook и измерить полное восстановление.
- Rate limiting в памяти годится для одного тестового процесса, но не гарантирует единое ограничение при нескольких API-репликах.
- Находящиеся в `docs/screenshots/` прежние снимки не обновились в этом коммите. Визуальную приёмку конкретно STAGING браузера нельзя основывать на старых DEV-скриншотах.

## III. Решение

**Принимаем `INTERNAL SYNTHETIC STAGING GO`** в буквальном ограниченном смысле: изолированный стенд с синтетическими данными; проверка интеграции, багфикс, тестирование команды, без публичных пользователей и реальных клиентских данных.

**Не присваиваем `EXTERNAL PILOT GO` и тем более `PRODUCTION READY`.** Это отдельное решение владельца после инфраструктурных и организационных требований.

## IV. Практический следующий этап — не новый продуктовый гейт, а запуск инфраструктуры

1. **Утвердить инфраструктуру:** домен (и схема поддоменов), сервер/облако, DNS, доверенный TLS (Let's Encrypt с DNS-01 для wildcard либо сертификаты на конкретные поддомены), защищённый доступ к Console (VPN/IP allowlist), staging vs production окружения.
2. **Защитить секреты:** генерировать runtime/DB/JWT/owner secrets вне исходников, ограничить права и ротацию, удалить фиксированные значения из любых доступных внешне конфигураций. Отдельно проверить отказ запуска при слабом секрете.
3. **Закрыть эксплуатацию:** offsite backup, расписание, восстановление на отдельной машине, алерты, health/readiness, логирование с редактированием PII, контроль сертификатов.
4. **Прогнать браузерный путь через реальный HTTPS-хост**, проверить hostname/SNI, персональную ссылку и QR через Nginx, а также отсутствие утечек между тенантами. Использовать синтетические данные.
5. **Юридические и операционные условия реального пилота:** согласие/договор об обработке ПДн, политика конфиденциальности, обязанности оператора/бизнеса, правила доступа сотрудников, контакты поддержки и регламент инцидентов. Эквайринг/SMS можно отложить, если продукт честно работает без них и не обещает доставку SMS или онлайн-оплату.
6. **GO/NO-GO для первого реального салона:** отдельное письменное разрешение, ограничение числа сотрудников и клиентов, план отката и отключения записи, запасной процесс ручного ведения расписания.
