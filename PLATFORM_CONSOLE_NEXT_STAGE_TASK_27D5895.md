## 1. Архитектурное правило

Система состоит из **трёх независимых приложений**:

- `apps/booking-web` — публичная запись конкретной компании, определяется по домену/поддомену.
- `apps/business-crm` — CRM компании, tenant-scoped авторизация и RBAC.
- `apps/platform-console` — **только наша внутренняя SaaS-админка**, platform-scoped логин, роли и аудит.

Backend остаётся единым модульным монолитом. Новое приложение использует только `/api/v1/platform/*` и выделенный platform auth; нельзя заимствовать CRM membership как способ выдачи прав платформы. По умолчанию никакой персонал платформы не видит клиентские данные/CRM тенантов.

Развёртывание: отдельный домен, например `console.example.com`; в DEV `localhost:3002` при том же API и общей БД. Домен — пример, не резервировать и не публиковать реальные DNS-записи.

## 3. UI-модули Platform Console

### A. Overview
- KPI компаний, пробных и активных подписок, grace periods, ожидаемых ручного решения блокировок, платежей/начислений.
- «Требуют внимания» с чётко определёнными критериями и фильтрацией: просроченные, приближающийся срок, заявка на поддержку, ошибочный домен.
- Сводка в часовом поясе платформы, явные подписи «поступило», «начислено», «не оплачено».
- Пустые, loading/error состояния и переходы к конкретным карточкам.

### B. Companies
- Таблица компаний с поиском, фильтрами по городу, статусу, плану и жизненному циклу.
- Create tenant onboarding: общие сведения, владелец (приглашение), план, лимиты, домен; итоговая страница со статусом успеха.
- Доказанное отсутствие дублирующих slug/domain; одноразовый invite, повторная отправка с аннулированием предыдущего токена.
- Карточка компании: обзор, подписка, модули/лимиты, доступ/ответственные, адреса/домены, история активности, поддержка.
- Suspended/reactivate — **отдельные подтверждаемые действия**, причина/аудит/последствия, без немедленного удаления данных.

### C. Subscriptions & billing ledger
- Различать `subscription_status`, `invoice/charge_status`, `payment_status`, дату окончания, льготный период, `suspension_state`.
- Зафиксировать **единую политику**, исключающую противоречие дизайн-листа: для MVP рекомендовано ручное приостановление после grace, если владелец проекта не утвердил автоматическое. Состояние `pending_suspension` не означает фактическую блокировку.
- Начисления, ручная регистрация оплаты, частичная оплата, переплата, предотвращение дублей по idempotency key.
- Нельзя приравнивать «продлить доступ» к «получить деньги». Суммы в тиынах, корректное отображение KZT, аудит с прежним и новым значением.
- Изменение плана: старый/новый план, effective_at, версия тарифных ограничений и последствия для существующих пользователей/филиалов.

### D. Plans
- Список тарифов, создание и **версионирование изменений**; нельзя задним числом менять то, что начислялось по предыдущему тарифу.
- Цена, период, max_branches, max_staff, разрешённые модули, статус publish/archived.
- Переключатели «включено» должны быть реальными доступными с клавиатуры контролами, а не декоративными `span`.

### E. Modules
- Каталог модулей и фичефлагов: `catalog availability` vs `tenant entitlement` vs `configured/operational state`. Это три независимых сущности.
- Настройка модуля для конкретной компании только с подтверждением и аудированием.
- Запрещено глобальное включение незапущенного SMS/WhatsApp как реально работающей услуги. Не заявлять о работающих интеграциях без провайдера.

### F. Support
- Тикеты и связь с компанией, статусы, приоритеты, комментарии и история.
- Временный доступ **только** после явного approval владельца: requested → pending → approved/denied → active → expired/revoked.
- Время доступа ограничено (например, 30 минут по правилам дизайна), обязательные reason, tenant binding, scope, action audit.
- Никакого «notify owner = approved» и автоматического входа в чужую CRM. Привязка к той же компании после завершения запроса.

### G. Audit
- Поиск по времени, actor, tenant, action, статусу; read-only.
- Запись каждой высокорисковой операции (смена плана, оплата, права, support-access, блокировка) с request id, old/new, reason, actor, timestamp. Секреты и токены не записывать.
- Ограничения ролей, пагинация и стабильная сортировка.

### H. Settings
- Platform staff & RBAC: `platform_owner`, `finance`, `support`, `viewer` — уточнить фактически существующие enum/модели. Принцип минимальных прав.
- Конфигурация lifecycle, grace/manual suspension, уведомлений и общие сведения платформы.
- Не размещать API секреты, JWT и платёжные ключи внутри frontend; только безопасная конфигурация в окружении.

## 4. Согласованность прав и API

Для каждой операции должна быть серверная проверка **platform role**, не только скрытая кнопка. Тестировать минимум: owner/finance/support/viewer; запрет CRM staff открывать Platform API; запрет support вручную менять оплату/владельца/план; запрет finance на поддержку и RBAC; tenant scope на временные сессии. Сессия platform staff не должна быть взаимозаменяема с JWT пользователя CRM.

Единый DTO-контракт в `packages/api-client`: строгая типизация request/response, обработка 401, 403, 404, 409, 422, retry только для безопасных запросов, loading/empty/error UI.

Дополнить API по результатам матрицы. Миграции только Alembic, идемпотентность high-risk операций, строгая multi-tenant RLS, не ослаблять текущие tests 32/15.

## 6. Независимая приёмка

Обязательные non-vacuous E2E:

1. Platform owner создаёт tenant с валидным slug; выдаёт приглашение; владелец активирует аккаунт; новый tenant виден в Platform Console, а в его CRM отсутствуют записи другого tenant.
2. Вносится платёж частями; комиссия/сумма и остаток корректны, double-submit не создаёт вторую транзакцию.
3. Период trial/grace/ручная приостановка/восстановление последовательно отражаются в **Platform Console, CRM и публичной записи**. Все статусы фиксируются аудитом.
4. Finance не может открыть или изменить чужие данные CRM; support не может проводить оплату; viewer не может сделать запись/приостановку.
5. Запрос поддержки для компании A требует её owner approval, не активируется для компании B, корректно истекает и может быть отозван.
6. Запись через Booking Web компании A по-прежнему появляется в CRM A и не видна в CRM B (регрессия).
7. Для каждого крупного экрана есть screenshot после загрузки данных: с заполненными значениями и отдельный deliberate empty-state; ключевые состояния 390px, 1280px и 1440px. Изображения сравнить с оригиналом и объяснить отклонения.
8. При сбое backend/fetch UI показывает ошибку с retry, а не нули или «Нет компаний».
9. `npm run build --workspaces`, `pytest`, весь старый Playwright, новые E2E, миграции/CI — зелёные. Отдельно проверить `docker build`, если в итоговый gate включена production-like контейнеризация.

Запрещены условные `if (element.isVisible())` для обязательных проверок, фиктивные даты/суммы/аватары в API, production-ready заявления без среды и доставки транзакционных уведомлений.
