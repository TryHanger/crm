# Регламент аварийного восстановления и резервного копирования (RESTORE RUNBOOK)

Данный регламент устанавливает процедуру регулярного создания резервных копий и аварийного восстановления (Disaster Recovery) базы данных SaaS CRM.

---

## 1. Архитектура резервного копирования

Резервное копирование PostgreSQL автоматизировано скриптом [`scripts/backup_db.py`](scripts/backup_db.py).

### Характеристики резервной копии:
- **Формат**: Полный SQL-дамп схемы и данных (`--clean --if-exists`).
- **Контроль целостности**: Автоматический расчёт криптографического хеша **SHA-256**.
- **Манифест метаданных (`.manifest.json`)**:
  - Имя файла бэкапа и абсолютный путь.
  - Контрольная сумма `sha256_checksum`.
  - Размер файла в байтах.
  - Метка времени создания (UTC).
  - Версия утилиты `pg_dump` и целевая СУБД.
  - Статус создания (`SUCCESS`).

### Команда создания бэкапа:
```bash
python scripts/backup_db.py --output-dir backups --database saas_crm_test --verbose
```
Флаги:
- `--output-dir` / `--dir` / `-d`: целевой каталог сохранения (по умолчанию `backups`);
- `--database` / `--db`: имя базы данных для снятия дампа;
- `--verbose` / `-v`: подробный вывод информации о версии клиента и времени выполнения.

## 2. Процедура аварийного восстановления (Disaster Recovery)

Восстановление выполняется на изолированную чистую базу данных скриптом [`scripts/restore_db.py`](scripts/restore_db.py).

### Этапы процедуры:
1. **Строгая валидация манифеста (Fail-Fast)**:
   - При отсутствии файла манифеста процедура немедленно прерывается (`FileNotFoundError`). Восстановление неавторизованных дампов запрещено.
   - Вычисление SHA-256 хеша SQL-дампа и побайтовая сверка с `sha256_checksum`. При несовпадении — фатальная ошибка (`ValueError`).
2. **Инициализация целевой чистой БД**:
   - Принудительное завершение активных сессий целевой базы (`pg_terminate_backend`).
   - Имя целевой БД обязано оканчиваться на `_test` во избежание случайного затирания боевой БД.
   - `DROP DATABASE IF EXISTS <target_db>`, затем `CREATE DATABASE <target_db>`.
3. **Накатывание SQL-дампа**:
   - Выполнение потокового SQL через `psql` с обязательным флагом `-v ON_ERROR_STOP=1`.
   - Любой ненулевой код возврата или ошибка синтаксиса прерывает процедуру с фатальным кодом выхода.
4. **Комплексная автоматическая верификация**:
   - Проверка ревизии Alembic (`alembic_version`).
   - Подсчёт восстановленных таблиц (минимум 47 прикладных таблиц).
   - Подсчёт арендаторов, планов подписок, сотрудников и филиалов.
   - Аудит Row-Level Security: сканирование системного каталога `pg_class`, подтверждение флагов `rowsecurity=true` и `relforcerowsecurity=true` на **22 таблицах тенантов**.
   - Проверка ограничения исключения `staff_occupancy_no_overlap`.
   - **Аудит непривилегированного runtime-пользователя (`crm_app_user`)**: выполнение запроса к восстановленной БД от имени runtime-роли без контекста тенанта (возвращает 0 строк) и с контекстом тенанта (возвращает только строки соответствующего тенанта).

### Команда восстановления:
```bash
python scripts/restore_db.py --manifest backups/backup_saas_crm_test_20261109_120358Z.manifest.json --target-db saas_crm_restore_test --report backups/restore_verification_report.json --verbose
```
Флаги:
- `--manifest` / `-m`: путь к файлу манифеста JSON;
- `--backup` / `--source` / `-b`: путь к SQL-дампу (если не указан, берётся из манифеста или самый свежий в каталоге);
- `--target-db` / `--target` / `-t`: имя целевой тестовой БД (обязательно суффикс `_test`);
- `--report` / `-r`: путь для сохранения итогового отчёта верификации;
- `--verbose` / `-v`: подробный вывод.

## 3. Честные метрики непрерывности (RTO / RPO)

| Метрика | Норматив | Фактическое измерение | Текущий статус | Обоснование |
|---|---|---|---|---|
| **RTO (Recovery Time Objective)** | $\le 15$ мин | **1.69 – 2.26 сек** (потоковый SQL restore) / **~30–60 сек** (полный цикл со стартом контейнеров и прогревом) | **ВЫПОЛНЕНО** | Измеренная скорость применения SQL-дампа ~450 КБ на PostgreSQL 17 составляет $< 2.5$ с. Дополнительное время требуется на запуск сервисов и проверку health probes. |
| **RPO (Recovery Point Objective)** | $\le 1$ час | **1 час** (при часовом расписании cron) / **5 минут** (при WAL-архивации) | **PARTIAL** | Локальные снимки гарантируют RPO в 1 час. Для продакшн требуется включение WAL-g. |
| **Offsite Backup Storage** | Внешнее S3 / GCS хранилище | Отсутствует внешнее хранилище | **BLOCKED** | До подключения внешнего S3/SFTP хранилища снимки хранятся на локальном томе хоста. Не имитировать готовность до предоставления бакета. |
| **Верификация целостности** | 100% таблиц, данных и RLS | **47/47 таблиц**, **22/22 Forced RLS**, runtime role query PASS | **ВЫПОЛНЕНО** | Доказано автоматизированным тестом `test_disaster_recovery_negative_scenarios`. |

## 4. Регламент реагирования при сбое DR

1. **Сигнализация о сбое**:
   - При ненулевом коде возврата `backup_db.py` или `restore_db.py` выполнение прерывается с выбросом `RuntimeError`.
   - В CI/CD пайплайне шаг завершается с кодом `exit 1`.
2. **Действия дежурного инженера**:
   - Проверить журнал: `cat backups/restore_verification_report.json` или вывод консоли.
   - Проверить соответствие версий `pg_dump` и сервера PostgreSQL 17 (`pg_dump --version`).
   - Убедиться в целостности манифеста и контрольной суммы SHA-256.
   - Проверить права роли `crm_app_user` и доступность СУБД.
