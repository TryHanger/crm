## 2. Подтвержденные дефекты и недостающие потоки

### FC-P0-01: HTTP 500 вкладки «Доступы» компании — воспроизведено логами CI

Файл: `apps/api/app/api/v1/platform/routes.py`, обработчик `GET /api/v1/platform/tenants/{tenant_id}/users`, около строк 432–470.

- ORM `TenantMembership` содержит `joined_at`, **не** `created_at`, однако обработчик обращается к `m.created_at`.
- ORM `Invite` содержит `consumed_at`, **не** `accepted_at`, однако обработчик фильтрует `Invite.accepted_at == None`.
- В журнале успешного CI `42575445762` многократно зафиксирован HTTP 500 с обоими `AttributeError`.
- `CompaniesModule.loadTenantDetail()` перехватывает ошибку `getTenantUsers()` и заменяет результат на `null`; UI не сигнализирует о проблеме.

**Исправить:** использовать `m.joined_at`; выбирать `Invite.consumed_at.is_(None)` и `expires_at > now`, корректно различать `sent`/`pending` и не скрывать ошибку под пустым списком. Добавить API интеграционный тест с существующими membership и invite; E2E тест вкладки должен требовать конкретный email/роль/приглашение и ноль HTTP 500. Добавить CI gate по неожиданным ответам 5xx/ошибкам страницы на обязательных маршрутах. Не вводить новое поле миграцией только ради этого маппинга.

### FC-P0-02: отсутствует frontend активации платформенного оператора

- Backend `POST /api/v1/platform/staff/activate` реализован и покрыт тестами.
- `create_platform_staff()` возвращает путь `/activate-platform?token=...`, но `apps/platform-console/src/App.tsx` не обрабатывает `window.location.pathname` и у неавторизованного посетителя показывает только `PlatformLoginPage`.
- `PlatformSettingsModule.tsx` выбирает `res.activation_url || fullUrl`; сервер возвращает относительный URL, так что вместо полноценного абсолютного адреса в интерфейсе может оказаться только `/activate-platform?token=...`.

**Исправить:** полноценная публичная (без сессии) страница активации по URL, безопасное заполнение и подтверждение пароля, обработка expired/consumed/invalid токенов, переход к логину. Нормализовать URL через `new URL(path, window.location.origin).href`; не логировать токен и не передавать его в аналитику. E2E обязателен: пригласить нового оператора → открыть ссылку в чистом browser context → установить пароль → войти → повтор токена отклонён. Проверить, что токен не сохраняется в localStorage.

### FC-P0-03: риск сброса пароля уже существующего CRM пользователя при повышении роли

- `POST /platform/staff` позволяет `allow_crm_user_upgrade=True` для пользователя с CRM membership и возвращает одноразовый токен вызывающему платформенному админу.
- `POST /platform/staff/activate` всегда выполняет `user.password_hash = get_password_hash(req.password)`, включая **существующего** пользователя CRM.
- Поэтому платформа может пересоздать пароль существующего владельца/сотрудника CRM через приглашение и полученный токен, что нарушает границу владения учётной записью. Наличие явного флага не эквивалентно согласию владельца email/учётной записи.

**Исправить:** для существующей учётной записи активация платформенной роли только при аутентифицированном подтверждении этим пользователем (включая проверку политики усиленной аутентификации), **без изменения** его текущего пароля. Для нового аккаунта — процедура одноразовой установки пароля. Добавить отрицательный тест: оператор платформы с флагом upgrade и полученным токеном не может сменить пароль существующего CRM владельца без его участия; старый пароль пользователя продолжает работать.

### FC-P1-01: подтверждение запроса поддержки через API, но не через интерфейс владельца CRM

- Имеются `GET /business/access-requests/pending`, `POST .../approve`, `POST .../deny`.
- В `tests/e2e/platform.spec.ts` «владелец подтверждает» реализовано программным `request.post(...)` с токеном владельца, а не через браузерную форму Business CRM.
- В текущих `Business CRM App.tsx` и `SettingsModule.tsx` нет соответствующего UI-маршрута/экрана.

**Исправить:** в CRM владельца разместить список ожидающих запросов с организацией, запрашивающим, причиной, требуемой областью данных и сроком; кнопки согласия и отказа с явным подтверждением. У администратора и мастера не должно быть права согласия. Тест: оператор запрашивает → отдельный браузер владельца видит запрос → одобряет → оператор получает диагностику → владелец отзывает (если предусмотрено API) либо оператор отзывает, TTL блокирует доступ. Запрещено подменять взаимодействие UI вызовом `request.post` при приёмке сценария.

### FC-P1-02: фронтенд не обеспечивает стабильную идемпотентность оплаты после сетевого сбоя

- Backend корректно связывает ключ с charge_id, amount, evidence и method, проверяет остаток и использует row lock.
- `SubscriptionsModule.tsx` на каждую отправку создаёт ключ `pmt_${charge.id}_${Date.now()}`. При повторе после потери ответа ключ изменится, что ослабляет клиентскую гарантию от дублей.

**Исправить:** создать ключ единожды на конкретную пользовательскую попытку и сохранять его до достоверного ответа/проверки статуса; после неопределённого результата предложить рефетч Ledger и повтор с тем же ключом. E2E: первый ответ сервера теряется после записи БД → повтор по тому же ключу → единственный PaymentRecord; нельзя считать фиктивную строку доказательством реальной оплаты в банковской системе.

### FC-P1-03: сквозные контрольные условия

- На Platform Console для пользовательской вкладки, биллинга и поддержки исключить скрытые `catch(() => null)` / `catch(() => [])`, превращающие ошибки в ложные пустые состояния.
- Запретить хранение сырых одноразовых токенов в логах, URL аналитики, видеозаписях публичных тестов; DEV-учётные записи должны отсутствовать в production.
- Автоматические тесты должны проверять не только наличие модалок, а фактическое состояние PostgreSQL и бизнес-авторизацию.
- Тестировать подтверждение/отказ с разными tenants и их owner-аккаунтами, повтор запросов, истечение времени, отзыв, роли Viewer/Finance/Support.
