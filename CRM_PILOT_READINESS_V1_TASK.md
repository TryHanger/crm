## PR-1. Домены, reverse proxy и HTTPS

Пока только условные имена:
- `console.<STAGING_DOMAIN>` → Platform Console.
- `app.<STAGING_DOMAIN>` → Business CRM.
- `<tenant>.book.<STAGING_DOMAIN>` → Booking Web.
- `/api/v1/*` проксируется к общему FastAPI. Для public booking предпочтителен same-origin `/api` через доверенный proxy.

1. Убери захардкоженный `.book.example.kz` из создания TenantDomain; используй конфигурацию `BOOKING_DOMAIN_SUFFIX`. Аналогично конфигурируй `CRM_DOMAIN` и `PLATFORM_DOMAIN`.
2. Нормализуй Host/порт/IDNA; доверяй `X-Forwarded-Host` только от собственных прокси. Не допускай spoofing для подмены компании.
3. Подготовь HTTPS для конкретных разрешённых доменов; исключи wildcard CORS и смешение cookies между доменами. Не используй `*.example.kz` как реально зарегистрированный адрес.
4. Протестируй два изолированных tenant на разных Host: данные, цены, графики и брони компании A никогда не должны попасть в B.

**PASS:** три приложения и общий API работают по отдельным именам; у двух компаний нет перекрёстного доступа даже через прямые HTTP-запросы.

## PR-2. Реальный онбординг без демоданных

Полный сценарий: Platform Console создаёт tenant → приглашение владельцу → активация → вход в Business CRM → филиал, услуги, сотрудники и графики → публикация Booking Web → запись клиента.

1. Текущий `create_tenant` в non-DEV возвращает `invite_token=null` / `invite_url=null` и не организует доставку. Добавь реальный email-транспорт с контролируемыми повторными попытками и аудитом доставки. До подключения SMTP — честный безопасный ручной канал приглашения, если согласован владельцем пилота, **без ложных сообщений «отправлено»**.
2. Хешируй одноразовые токены, TTL и single-use, ограничь частоту выдачи/активации. Не логируй токены, пароли и ссылки с токенами.
3. Существующий CRM-пользователь при присоединении к новой компании/платформенной роли не должен терять пароль или получать доступ без подтверждения.
4. Не использовать `Password123!`, seeded platform/tenant users и автологин в окружении с реальными пользователями.
5. Для операторов Platform Console до появления полноценного MFA защищай STAGING через VPN/IP allowlist и контролируй список допущенных людей.

**PASS:** новый владелец без предсозданного аккаунта проходит путь от приглашения до настройки своей CRM.

## PR-3. Эксплуатационная безопасность

1. Секреты и доступы к БД только через защищённые runtime-переменные/secret store; в staging fail-fast при дефолтных JWT и DB credentials. Не сохраняй `.env` в Git, ZIP и журналы.
2. Ограничение запросов: логин, активация, invite, public booking, self-management token, support. Проверить 429 и нормальный пользовательский поток.
3. Отрицательные тесты 401/403: master, owner другой компании, viewer, support, finance, expired/revoked support session; RLS в PostgreSQL под runtime-ролью.
4. Мониторинг: health/readiness, structured request IDs, ошибки API, задержки и алерты; строго без персональных данных и bearer-токенов в логах.
5. Проверить хранение `platform_token` в `localStorage` как отдельный security risk; перед внешним доступом к админке оценить переход на более безопасную схему сессий, защиту от XSS, logout/revoke, ограничение времени жизни.
6. Ручной Billing Ledger: не выдумывать оплату. Renewal, charge и запись подтверждённого платежа остаются разными операциями, с идемпотентностью.

**PASS:** негативные security smoke tests проходят; доступ поддержки строго owner-approved, 30 минут, read-only и мгновенно отзывной.

## PR-5. Строгие сквозные пилотные тесты

Обязательны минимум две компании на отдельном STAGING: кандидат пилота (пока на тестовых данных) и контрольный tenant.

- Platform owner создаёт компанию; приглашённый владелец принимает ссылку через браузер и активирует доступ без DEV seed.
- Владелец настраивает филиал, timezone, график, услуги/цены; страница бронирования отображает данные.
- Клиент записывается тремя способами; `booking_id/public_ref` совпадает в Booking Web и CRM, отмена/перенос отражаются сразу.
- Гонка за последний слот и сетевой retry не создают двойные записи.
- Изменение рабочего графика и персональных цен сразу корректно учитывается в availability.
- A не видит B ни по Host, ни по `tenant_id`, ни по CRM API.
- Безусловный тест поддержки: запрос → owner approval UI → доступ → отзыв → немедленный 403.
- Отдельные тесты suspend/reactivate, renewal без оплаты, подтверждённого ручного платежа, истёкших токенов, timezone-границ суток.
- Viewport 320/390/1280, отсутствие критичных 500 и несанкционированных 200. Все assertions обязательные — не маскировать дефекты `if (visible)`.

**PASS:** реальный браузерный вертикальный сценарий с журналом запросов, trace и санитизированными скриншотами.
