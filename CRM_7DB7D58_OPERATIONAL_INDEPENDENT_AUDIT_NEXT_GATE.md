## 2. Стоп-факторы для принятия текущего коммита

### P0-01 — frontend asset sync регрессия и 403 через Nginx

- Файл `Dockerfile.frontend`: команда `cp -rn /opt/static/{app}/. /var/www/{app}/` выполняется от `USER 101:101`.
- **Независимо воспроизведён** конкретный риск на BusyBox `cp -rn src/. dst/`, когда `dst/` уже существует: код возврата **0**, но `index.html` не копируется. Это соответствует признакам CI: контейнер работает, а Nginx отвечает 403 (вероятно, из-за отсутствующего индекса). На точном `nginx:1.27-alpine` необходимо подтвердить наличие/отсутствие файлов и посмотреть `nginx error.log` перед фиксом.
- Исправить копирование содержимого всех трёх frontend (Booking Web, Business CRM, Platform Console) без `-n` на существующих каталогах. Предпочтителен простой безопасный `cp -a /opt/static/<app>/. /var/www/<app>/` либо атомарная синхронизация, совместимая с непривилегированным UID. Не возвращать runtime root.
- **Обязательные проверки:** `test -s /var/www/booking-web/index.html`, то же для `business-crm`, `platform-console`; в контейнере Nginx файлы читаются; выдать `200` для всех 3 HTTPS frontend-host, обслужить JS/CSS bundle (`200`, правильный Content-Type), неизвестный Host даёт 404. `frontend` healthcheck должен проверять assets, а `proxy` должен ждать его `service_healthy`, чтобы исключить race condition при холодном старте.
- Добавить отрицательный тест пустого volume: запуск на `down -v` с чистым каталогом и повторный запуск без удаления volume. Оба обязаны отдавать содержимое актуальной сборки.

### P0-02 — жёстко заданный fallback-ключ AES-256-GCM

- Файл `scripts/offsite_backup.py`, функция `derive_or_get_encryption_key`: при отсутствии `BACKUP_ENCRYPTION_KEY` берётся SHA-256 от встроенной неизменной строки.
- Это **неприемлемо для любой реальной резервной копии**, даже зашифрованной. Ключ полностью вычисляется из исходного кода.
- Изменить на **fail-closed**: отсутствие корректного высокоэнтропийного 32-байтного ключа (строго определённое представление, например 64 hex-символа) = ошибка и ненулевой exit code. Не хэшировать произвольную пользовательскую парольную строку в ключ шифрования. Создание ключа — отдельная явная команда с CSPRNG; сам backup-script его не генерирует незаметно при каждом запуске. В CI передавать ephemeral random test key из секретного окружения и уничтожать после прогона. Ключ не выводить, не включать в ZIP, манифест или логи.
- Негативные тесты: ключ отсутствует, неверная длина, неверный hex, случайный чужой ключ, испорченный ciphertext / GCM tag — операция должна завершаться FAIL.

### P0-03 — файл `.env.staging` с секретами без гарантированных прав

- Файл `scripts/generate_staging_secrets.py`, `write_env_file`: обычный `open(path, 'w')` без `chmod`, атомарного безопасного создания или контроля уже существующих прав. На системах с `umask 022` файл обычно доступен для чтения другим локальным пользователям (`0644`).
- Использовать безопасное создание с `O_CREAT | O_EXCL` и режимом `0600` (либо кратковременно `umask(0o077)` с восстановлением исходного umask), атомарную запись/rename и обязательную проверку `stat().st_mode & 0o077 == 0` для POSIX. Не выводить даже первые символы административного пароля в лог. Существующие файлы с небезопасными правами не игнорировать молча.
- При повторном запуске не заменять рабочие секреты и не выполнять автоматическую ротацию без отдельной операции; подтвердить сохранение существующих значений.

### P1-04 — заявленное S3 offsite отсутствует в коде

- Файл `scripts/offsite_backup.py`: при наличии `OFFSITE_S3_BUCKET`, `OFFSITE_S3_ACCESS_KEY`, `OFFSITE_S3_SECRET_KEY` присваивает статус **`READY_TO_UPLOAD`** и пишет его в манифест. Вызова S3 `PutObject`, multipart upload, `HeadObject`, сверки скачанного объекта, retries и remote retention **нет**.
- Поэтому текущая функция — **локальное создание зашифрованного пакета**, а не работающий offsite backup. Исправить документацию и статусы: `LOCAL_ENCRYPTED_BACKUP_READY`, `REMOTE_UPLOAD_NOT_IMPLEMENTED`, `BLOCKED`; *никогда* `OFFSITE_SUCCESS` до подтверждения удалённого объекта.
- Реальный S3 upload внедрять отдельной узкой задачей после выбора провайдера и выдачи тестового бакета/учётных данных; использовать минимальные IAM права, HTTPS, таймауты и негативные тесты upload failure. Если ресурсы отсутствуют, честно оставить `BLOCKED`, без мока в качестве основания для PILOT GO.
- Исходный plaintext `.sql` после шифрования остаётся на локальном диске. Определить защищённое расположение, TTL/retention и безопасную процедуру удаления временного plaintext в случае успеха или ошибки (не потерять единственную рабочую копию при сбое).

### P1-05 — ложное «полное RTO»

- `verify_offsite_restore` измеряет расшифровку `.enc`, распаковку `.gz` и восстановление локальной тестовой БД; это *время локальной процедуры*, не полный RTO бизнес-сервиса.
- Не входят обнаружение инцидента, provision нового VPS, загрузка из удалённого хранилища, восстановление env/secret, запуск контейнеров, проверка DNS/TLS и полноценные пользовательские запросы.
- Переименовать метрику в `local_encrypted_archive_restore_duration_seconds`; реальный операционный RTO/RPO определить только после disaster-recovery drill на отдельном хосте и измерения. Не писать утверждения «боевой RTO 15–25 секунд» без подтверждения.

### P1-06 — название tenant-isolation теста завышает покрытие

- `scripts/verify_staging_e2e_flow.py` под названием `multi_tenant_isolation_check` запрашивает чужую карточку **без любого access token** и получает 401/403. Это проверка **authentication enforcement**, не межтенантной изоляции.
- Добавить второго независимого тенанта B, настоящий owner B с корректным JWT, активную запись у A и прямой запрос owner B к ID записи A: строго 403/404; аналогично A к данным B. Для публичных host подтвердить, что данные и бронирования не смешиваются. Назвать текущую проверку `unauthenticated_access_rejection`.

### P1-07 — чрезмерно широкий default platform allowlist

- `generate_staging_secrets.py` по умолчанию задаёт `PLATFORM_IP_ALLOWLIST=127.0.0.1,::1,172.28.0.0/16,10.0.0.0/8`. Для реального стенда это расширяет допустимые внутренние источники и не означает доступ только из VPN.
- Для CI допускаются точные заранее определённые адреса. Для эксплуатационного окружения требовать явный список конкретных CIDR администратора/VPN, без автоматического допуска `10.0.0.0/8`. Сохранить независимые RBAC/JWT проверки; IP allowlist — лишь дополнительная граница.

## 3. Критерии итогового Gate

### CI и Runtime
1. Ветка от `7db7d589d5f34ce36c53aa711c88754ccac30744`, только feature, commit/push разрешён, без merge и production deploy.
2. Полный зелёный GitHub CI **того же HEAD** (все 48 backend и существующие Playwright тесты, frontend build, container TLS, контейнерный API E2E, восстановление DR). Не объявлять тесты выполненными, если workflow их пропустил.
3. После `docker compose down -v` полностью чистый `up`, проверка assets `index.html` на обоих контейнерах и HTTP `200` + HTML + JS/CSS через 3 различных SNI/Host. Повторный deploy без удаления данных; миграции успешно завершаются.
4. `nginx -t`, positive/negative TLS hostname verification, неизвестный `Host` / незарегистрированный tenant => 404.
5. Сквозной `scripts/verify_staging_e2e_flow.py` проходит через контейнерный HTTPS и действительно создаёт запись A; отдельный owner B не может прочитать A (не просто анонимный 401).

### Секреты и DR
1. Обязательный случайный ключ AES-256-GCM, тесты корректного шифрования, tamper detection, отсутствующего/некорректного ключа.
2. `.env.staging` гарантированно `0600`, не публикуется в artifacts, Git, логи или ZIP.
3. Локальный encrypted package+restore проверен; remote upload прямо BLOCKED, если не существует настоящего S3; в отчёте не называем его offsite successful.
4. Сохранены доказательства ID-level A/B изоляции в PostgreSQL restore под runtime-role без `BYPASSRLS`; статус DR fail-closed.
5. Время локального восстановления отделено от гипотезы будущего RTO/RPO.

### Отчётность
- `git diff --stat`, полный SHA, ссылки на workflow и артефакты, `git status`, версии Docker/Postgres/Node/Python.
- Контейнерные логи `frontend`, `proxy` (включая Nginx error.log в момент 403), проверка `ls -l` для `index.html` и asset manifests, Nginx response headers.
- Отчёт о статусе каждого критерия `PASS/PARTIAL/BLOCKED`, без общих фраз «всё успешно» при failed CI.
- ZIP только с кодом, зависимостями, протоколами, обезличенными артефактами. Без `.env`, приватных ключей, дампов, raw-token или реальных ПДн.
