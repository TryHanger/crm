# Отчет о прохождении защитных барьеров безопасности (SECURITY_GATES.md)

В данном документе зафиксировано соответствие архитектуры и реализации четырем критическим барьерам надежности (Security Gates A, B, C, D).

---

## Gate A: Воспроизводимость и конфигурация (Config & Reproducibility)

- **Статус:** **ВЫПОЛНЕНО (PASS)**
- **Зависимости:** Управление через стандартный `pyproject.toml` (PEP 621) и `requirements.txt`. Версии библиотек `fastapi==0.115.6`, `uvicorn==0.34.0`, `sqlalchemy==2.0.36`, `asyncpg==0.30.0`, `psycopg2-binary==2.9.10`, `alembic==1.14.0`, `passlib[bcrypt]==1.7.4`, `bcrypt==4.0.1` зафиксированы.
- **Окружения:** Разделены профили `development`, `test`, `production` через `ENVIRONMENT`. При запуске в `production` проводится обязательная валидация на запрет использования секретов по умолчанию и wildcard CORS `["*"]`.
- **Изоляция тестов:** Тесты выполняются исключительно на выделенной БД `saas_crm_test`. Проверка в `conftest.py` гарантирует отказ выполнения тестов, если имя БД не заканчивается на `_test` или окружение выставлено в `production`.
- **Контейнеризация:** Двухстадийный `Dockerfile` компилирует зависимости во временном слое сборки с `libpq-dev` и запускает API в легковесном слое от имени непривилегированного пользователя `appuser`. Включен healthcheck через `/health/live`.

## Gate B: Аутентификация и многоарендная изоляция (Auth & Tenant Isolation)

- **Статус:** **ВЫПОЛНЕНО (PASS)**
- **Хэширование паролей:** Бэкдор `dev_secret_hash` полностью удален из кодовой базы. Все пароли пользователей хэшируются с использованием `bcrypt` (12 раундов) и проверяются только криптографическим сравнением `pwd_context.verify`.
- **Row-Level Security (RLS):** База данных использует роль `crm_app_user WITH NOSUPERUSER NOBYPASSRLS`. На всех 21 таблице арендатора включен `FORCE ROW LEVEL SECURITY`. Сессионная переменная `app.current_tenant_id` устанавливается при каждом запросе через middleware и зависимости.
- **Управление клиентскими записями:** Поиск токена бронирования выполняется через функцию `lookup_public_management_token` с модификатором `SECURITY DEFINER SET search_path = public`, предоставляя минимальные привилегии без раскрытия таблицы токенов напрямую.
- **Связность данных:** Межарендные внешние ключи исключены на уровне схемы БД составными ключами `(tenant_id, id)` и проверены тестом `test_cross_tenant_foreign_key_prevention`.

## Gate C: Права доступа ролей и разграничение полномочий (RBAC & Master Scoping)

- **Статус:** **ВЫПОЛНЕНО (PASS)**
- **Линейный персонал (Master):**
  - **Календарь:** Видит в расписании исключительно свои рабочие слоты и записи (`/api/v1/business/calendar`). Попытка запросить календарь без привязанного профиля мастера блокируется `403 Forbidden`.
  - **Карточка записи:** Доступ к карточке (`GET /api/v1/business/bookings/{id}`) ограничен только своими записями. При попытке открыть чужую возвращается `403 Forbidden`.
  - **Изменение статуса, перенос и отмена:** Мастер может переводить статус, переносить или отменять только свои записи.
  - **Клиентские данные:** В списке клиентов мастер видит только тех, кто ранее записывался лично к нему, при этом телефон клиента маскируется (`+7701***0001`).
  - **Финансы и отчеты:** Доступ к дашборду выручки и аналитики (`GET /api/v1/business/reports/overview`) доступен только ролям `owner` и `admin`. Попытка входа мастера блокируется с `403 Forbidden`.
- **Тарифные лимиты (Entitlements):** Создание филиалов и добавление персонала проверяются функцией `check_tenant_entitlement_limit`. При превышении лимита тарифа возвращается `403 ENTITLE_LIMIT_EXCEEDED`.

## Gate D: Надежность Booking Engine и защита от гонок (Booking Integrity & Concurrency)

- **Статус:** **ВЫПОЛНЕНО (PASS)**
- **Защита от овербукинга:** На уровне PostgreSQL наложена физическая блокировка через Exclusion Constraint:
  ```sql
  CONSTRAINT staff_occupancy_no_overlap EXCLUDE USING gist (
      tenant_id WITH =,
      staff_id WITH =,
      tstzrange(starts_at_utc, ends_at_utc, '[)') WITH &&
  )
  ```
  При одновременной попытке занять один и тот же слот двумя независимыми клиентами ровно один запрос завершается успехом (201 Created), а второй мгновенно отклоняется с ошибкой 409 Conflict без нарушения целостности данных.
- **Единый Authoritative Валидатор:** Создание, перенос и подтверждение записей проходят через функцию `validate_slot_and_policies`:
  - Проверка блокировки компании (`TENANT_SUSPENDED`)
  - Проверка активности филиала и мастера
  - Проверка рабочих смен мастера в таймзоне филиала (`STAFF_OUTSIDE_SHIFT`)
  - Проверка обеденных перерывов мастера (`STAFF_ON_BREAK`)
  - Проверка утвержденных отпусков и отгулов мастера (`STAFF_TIME_OFF`)
  - Проверка блокировок календаря филиала (`CALENDAR_BLOCKED`)
  - Проверка минимального времени предзаказа (`SLOT_TOO_SOON`) и горизонта бронирования (`SLOT_TOO_FAR`) для онлайн-записи
- **Идемпотентность:** При повторе сетевого запроса с тем же `Idempotency-Key` система не создает дублирующую запись, а возвращает существующее бронирование с рабочим токеном управления.
- **Многосервисная запись:** Расчет длительности и стоимости учитывает индивидуальные переопределения мастера (`StaffServiceOffer`), фиксируя финансовый и временной снимок на момент создания записи.
