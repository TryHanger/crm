# Известные ограничения и статус реализации (KNOWN_LIMITATIONS.md)

В данном документе честно и прозрачно зафиксированы текущие эксплуатационные ограничения, отложенные интеграции и особенности локального окружения.

---

### 1. Статус компонентов платформы

| Компонент / Модуль | Текущий статус | Описание и обоснование |
|---|---|---|
| **Multi-Tenant RLS & БД** | **PRODUCTION-READY** | PostgreSQL 17 с `btree_gist`, Exclusion Constraints, `crm_app_user` с `NOSUPERUSER NOBYPASSRLS`. Полная изоляция арендаторов, защита от утечек данных между тенантами. |
| **Booking Engine** | **PRODUCTION-READY** | Authoritative валидация смен, перерывов, отпусков, блокировок, лимитов предзаказа и горизонта. Гарантия защиты от овербукинга через PostgreSQL Exclusion Constraints. |
| **RBAC и разграничение ролей** | **PRODUCTION-READY** | Строгое разделение прав `platform_owner`, `platform_admin`, `finance`, `owner`, `admin`, `master`. Мастера изолированы от чужих записей и финансов. Номера телефонов клиентов маскируются. |
| **Ручной биллинг (Ledger)** | **PRODUCTION-READY** | Выставление начислений (`SubscriptionCharge`), учет платежей (`PaymentRecord`) с частичной оплатой (`partially_paid`) и идемпотентностью. |
| **Booking Web Frontend (`apps/booking-web`)** | **PRODUCTION-READY (Barbershop)** | Реализовано на React 19 + TypeScript в точном соответствии с дизайном `готовый фронт.html` (`tpl-desktop.html`, `tpl-mobile.html`, `tpl-res-desktop.html`). Поддерживает все сценарии: выбор филиала, категорий, услуг, мастеров, слотов с группировкой утро/день/вечер, подтверждение записи, экран успеха с кодом визита и самообслуживание по токену (отмена и перенос). |
| **Business CRM Dashboard (`apps/business-crm`)** | **MINIMAL REAL CALENDAR (PHASE 1)** | Реализована дневная сетка календаря с колонками мастеров и часовыми слотами (09:00 - 20:00), цветными бейджами статусов, модальным окном изменения статуса визита и переключателем компаний с проверкой изоляции записей. Сложный Drag-and-drop перенос в сетке и конструктор графиков смен запланированы на следующий этап. |
| **Platform Console Frontend** | **DEFERRED (BY DESIGN)** | В соответствии с прямым указанием («Не занимайся пока полным интерфейсом Platform Console, стоматологией и другими нишами»), интерфейс Platform Console отложен; backend API консоли платформы полностью функциональны (`/api/v1/platform/*`). |
| **Стоматология и другие ниши** | **DEFERRED (BY DESIGN)** | Опросники здоровья, зубные карты и специализированные медицинские протоколы вынесены в будущие релизы вертикальных расширений. |
| **SMS-уведомления** | **SIMULATED / PLANNED** | В соответствии с ТЗ и архитектурой интеграция со сторонними платными SMS-шлюзами (Twilio/SMSC) не подключалась. Записи событий аудита и уведомлений логируются в БД (`booking_events`). |
| **Банковский эквайринг (Касса/Сбер/Kaspi Pay)** | **DEFERRED (BY DESIGN)** | Оплата подписок платформы на текущем этапе реализована через ручной учет безналичных банковских платежей с подтверждающими документами (`evidence_reference`), что соответствует архитектурному документу. |
| **Фоновые периодические воркеры (Celery/Cron)** | **PARTIAL** | Все операции изменения статусов подписок и пересчетов выполняются синхронно в рамках транзакций API. Фоновый планировщик для ночной автоматической блокировки просроченных счетов зафиксирован в архитектуре и вынесен в следующий релиз. |
| **Docker Build на хосте** | **BLOCKED BY HOST DAEMON** | Файлы `Dockerfile` (двухстадийный non-root образ) и `docker-compose.yml` приведены в полное соответствие с требованиями. На хост-машине Windows служба Docker Desktop (`com.docker.service`) остановлена пользователем, поэтому выполнение `docker build` в текущей сессии заблокировано состоянием ОС хоста. |

### 2. Рекомендации перед коммерческим развертыванием (Production Rollout)
1. **Запуск Docker Desktop**: Запустить службу Docker Desktop на сервере развертывания для запуска собранного контейнера.
2. **Переменные окружения**: Задать уникальный криптостойкий `JWT_SECRET_KEY` (длиной от 32 байт) и настроить белый список доменов в `CORS_ORIGINS`.
3. **SMS-провайдер**: Подключить рабочий API-ключ выбранного SMS-шлюза в модуле нотификаций.
4. **Резервное копирование**: Настроить периодический `pg_dump` с шифрованием для базы данных PostgreSQL.
