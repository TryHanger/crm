# M02 · D2 · Компания и приглашение владельца: release note

Ветка: `d2/m02-owner-invite` (от `d2/m01-baseline`).

## Что сделано

| Задача | Результат |
|---|---|
| M02-D2-01 атомарный workflow | Создание компании вынесено в `apps/api/app/modules/onboarding/service.py`. Компания, домен, настройки записи, владелец, membership, приглашение и триал-подписка пишутся одной транзакцией вместе с аудитом. Письмо уходит только **после** коммита. Неизвестный тариф даёт 422 `PLAN_NOT_FOUND`, раньше молча подставлялся любой активный. Slug должен быть DNS-меткой (3–48 символов, `a-z0-9-`), системные имена (`api`, `admin`, `crm`…) запрещены. Дубль, в том числе при гонке, даёт 409 `SLUG_TAKEN`, а не 500. |
| M02-D2-02 токены, срок, повтор | `accept-invite` блокирует строку приглашения: из параллельных активаций проходит ровно одна. Короткий пароль или неверный текущий пароль приглашение не тратят. `resend-invite` ротирует ссылку (старая сразу перестаёт работать), умеет перевыпускать просроченные. Новых приглашений он больше не создаёт, после активации отвечает 409 `INVITE_ALREADY_ACCEPTED`. Во вкладке «Доступы» просроченные приглашения видны со статусом `expired`. |
| M02-D2-03 тесты и выпуск | `apps/api/tests/test_onboarding.py`, 18 тестов. `scripts/smoke_onboarding.py` проходит «создать → пригласить → войти» через origin Platform Console и CRM. Smoke подключён к `dev_stack.py --smoke` и к CI. |

## Закрытые дыры (были в коде до спринта)

1. `resend-invite` с любым email создавал приглашение **с ролью owner**. Оператор поддержки мог выдать владение компанией постороннему адресу.
2. `resend-invite` возвращал сырой токен в ответе во всех окружениях, включая production.
3. После активации владельца `resend-invite` отвечал «sent», но выдавал нерабочую ссылку.
4. Письмо с токеном отправлялось до коммита: при сбое коммита ссылка вела на несуществующую компанию.
5. Параллельные `accept-invite` одной ссылкой проходили все. Мутационная проверка: без блокировки строки тест падает 3 раза из 3.
6. Имя владельца и название компании вставлялись в HTML письма без экранирования.
7. Platform Console при доставленном письме показывала ссылку `…?token=undefined`.

## Изменения контракта API

- `POST /platform/tenants`: ошибки отдаются как `{"detail": {"code", "message"}}` (`SLUG_INVALID`, `SLUG_RESERVED`, `SLUG_TAKEN` 409, `PLAN_NOT_FOUND`). В ответ добавлено поле `invite_expires_at`.
- `POST /platform/tenants/{id}/resend-invite`: тело `{"email"}` валидируется как email. 404 `TENANT_NOT_FOUND` / `INVITE_NOT_FOUND`, 409 `INVITE_ALREADY_ACCEPTED`. `status` теперь отражает доставку (`sent` / `manual_channel_required` / `delivery_failed`). `invite_token` отдаётся только в dev/test, `invite_url` только если письмо не доставлено.
- `GET /platform/tenants/{id}/users`: `invites` содержит и просроченные (`status: "expired"`), по одной записи на email.
- `POST /auth/accept-invite`: коды не изменились (400 для неверной, использованной или просроченной ссылки), тексты ошибок стали точнее.
- В тестах slug с `_` (`susp_`, `hijack_`, `royal_`, `iso_`) заменены на `-`: подчёркивание недопустимо в DNS-имени поддомена.

## Ограничения

- Playwright E2E локально не запускались (браузеры Playwright не установлены). `platform.spec` и `pilot_readiness.spec` ждут ссылку в мастере, в dev она по-прежнему отдаётся.
- Реальная доставка писем: SMTP не настроен, это задача M15.
- Приглашения сотрудников из CRM (`/business/invites`, зона D1) ещё не проходят через этот сервис. Повторная отправка для них возвращает ссылку для ручной передачи.
- Если отозвать membership, его непогашенные приглашения останутся живыми. Кандидат в M15 (роли).
