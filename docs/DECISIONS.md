## 2. Архитектурные решения (ADRs)

### ADR-001: Мультитенантность и Row-Level Security (RLS)
- **Контекст:** Требуется изолировать данные сотен независимых компаний внутри единой базы PostgreSQL (Shared Database, Shared Schema) без риска межорганизационной утечки данных (Cross-Tenant Data Leakage / BOLA).
- **Решение:**
  1. Каждая tenant-таблица содержит столбец `tenant_id UUID NOT NULL`.
  2. Межтабличные связи между tenant-сущностями используют композитные внешние ключи: `FOREIGN KEY (tenant_id, foreign_id) REFERENCES target_table(tenant_id, id)`.
  3. В PostgreSQL включен принудительный RLS: `ALTER TABLE ... FORCE ROW LEVEL SECURITY`.
  4. Политика RLS проверяет: `tenant_id = NULLIF(current_setting('app.current_tenant', true), '')::uuid`.
  5. Контекст `app.current_tenant` выставляется транзакционно через `SET LOCAL` только после серверной проверки аутентификации пользователя или подтверждённого поддомена. При отсутствии контекста доступ запрещён (Fail Closed).
  6. Runtime-пользователь БД не имеет привилегии `BYPASSRLS`.

### ADR-002: Booking Engine и предотвращение двойного бронирования (No Overbooking)
- **Контекст:** Высокая вероятность параллельных запросов на один и тот же слот от двух клиентов или конфликт между ручной записью в CRM и публичной онлайн-записью.
- **Решение:**
  1. Создана таблица `staff_occupancies` как единый источник правды о занятости сотрудника во всех филиалах компании.
  2. Включено расширение `btree_gist` и добавлен PostgreSQL Exclusion Constraint:
     ```sql
     ALTER TABLE staff_occupancies
       ADD CONSTRAINT staff_occupancy_no_overlap
       EXCLUDE USING gist (
         tenant_id WITH =,
         staff_id WITH =,
         tstzrange(starts_at_utc, ends_at_utc, '[)') WITH &&
       ) WHERE (released_at IS NULL);
     ```
  3. Как подтверждённые брони (`bookings`), так и блокировки расписания (`calendar_blocks`) создают запись в `staff_occupancies`.
  4. При одновременных попытках занять слот на уровне PostgreSQL гарантируется, что ровно одна транзакция будет закомичена, а вторая получит `exclusion_violation`, транслируемый API в HTTP 409 `SLOT_CONFLICT`.
  5. Перенос записи (`reschedule`) выполняется атомарно в одной транзакции: освобождение старого слота и попытка занять новый. При конфликте транзакция откатывается, сохраняя старую запись нетронутой.

### ADR-003: Индивидуальные цены и длительности услуг у мастеров
- **Контекст:** В барбершопах старший мастер может стричь быстрее или дороже, чем стажер. Несколько услуг в одной записи должны выполняться последовательно.
- **Решение:**
  1. В `services` фиксируются базовые `base_price_minor` и `base_duration_minutes`.
  2. В таблице `staff_service_offers` хранятся переопределения `price_override_minor` и `duration_override_minutes` для конкретной пары (сотрудник, услуга, филиал).
  3. При поиске слотов и создании брони итоговая длительность рассчитывается как сумма длительностей услуг именно у выбранного мастера, а итоговая стоимость — как сумма цен.
  4. При подтверждении брони снапшоты длительности, названия и стоимости фиксируются в `booking_items`. Последующее изменение прайс-листа компанией никогда не изменяет финансовые и временные параметры ранее созданных записей.

### ADR-004: Жизненный цикл SaaS-подписок и ручной биллинг
- **Контекст:** На этапе MVP онлайн-платежи через внешние эквайринги не подключены; оплата производится по счетам/квитанциям.
- **Решение:**
  1. Новые компании создаются со статусом подписки `trial` (14 дней).
  2. По окончании trial наступает льготный период `grace` (7 дней), в течение которого онлайн-запись и CRM продолжают функционировать с предупреждением в интерфейсе.
  3. По истечении grace статус меняется на `expired_pending_action`. Автоматической блокировки нет; приостановка (`suspended`) производится вручную уполномоченным сотрудником платформы с фиксацией причины в аудите.
  4. Платформа ведет ручной реестр начислений (`subscription_charges`) и оплат (`payment_records`) с прикреплением реквизитов платежных документов.
  5. Приостановка (`suspended`) немедленно блокирует новые публичные записи и переводит CRM в режим чтения, но сохраняет всю историю и контакты.
  6. Реактивация (`reactivate`) восстанавливает полный доступ компании.

### ADR-005: Безопасность, OIDC и ограниченный доступ поддержки (Assistance Access)
- **Контекст:** Сотрудники платформы (Platform Console) не должны иметь неконтролируемого доступа к персональным данным клиентов компаний (PII) и конфиденциальным заметкам мастеров.
- **Решение:**
  1. По умолчанию Platform Console отображает только агрегированные технические и биллинговые метаданные (число филиалов, объем записей, статус системы).
  2. Для диагностики проблемы служба поддержки инициирует `support_access_request` с указанием скоупа и обоснования.
  3. Владелец компании (`owner`) должен явно подтвердить запрос в CRM (`/api/v1/business/access-requests/{id}/approve`).
  4. После подтверждения создается временная сессия с максимальным TTL 30 минут, которая может быть в любой момент отозвана владельцем.
  5. Все действия во время такой сессии регистрируются в неизменяемом журнале аудита `platform_audit_events`.
  6. Управление записями клиентом выполняется по одноразовым криптографическим токенам (`public_management_tokens`), хранящимся в хешированном виде (SHA-256) без раскрытия авторизационных данных CRM.

### ADR-006: Серверное определение тенанта по проверенному домену (Host Resolution)
- **Контекст:** Все компании работают через единую кодовую базу фронтенда онлайн-записи. Backend должен определять арендатора строго и безопасно.
- **Решение:**
  1. Идентификатор тенанта извлекается исключительно на основе заголовка `Host` (или проверенного `X-Forwarded-Host` от доверенного reverse proxy).
  2. Host нормализуется (нижний регистр, удаление порта) и валидируется по таблице `tenant_domains` со статусом `active` и `verified`.
  3. Любые попытки передачи `X-Tenant-ID` от клиента в публичном API игнорируются.
  4. Если домен не зарегистрирован или не опубликован, backend возвращает HTTP 404 `SITE_NOT_FOUND` без раскрытия списка существующих компаний.
